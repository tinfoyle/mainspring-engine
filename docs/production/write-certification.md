# Synthetic Work write and idempotency certification

Status: executable bounded evidence tool; connected staging execution remains a release gate

## Purpose

`cmd/write-cert` exercises the production routed Work-create boundary with dedicated synthetic Accounts. Every logical operation sends one generated request and then immediately repeats the exact body and `Idempotency-Key`. A passing result proves that both responses have the same status, weak ETag, Location, and body digest while create and replay latency remain inside predeclared per-Account budgets.

This complements the GET-only driver in [Account load and fairness certification](load-certification.md). It does not certify arbitrary mutations, cleanup, transitions, runner fairness, autoscaling, managed failover, or provider behavior.

## Safety boundary

The command is intentionally not a general write generator:

- The only target is `POST /api/v1/accounts/{account_id}/work-items` on one exact HTTPS origin.
- Payloads are generated by the compiled command. A plan cannot supply a path, title, description, assignment, due date, or arbitrary JSON.
- Generated items are ordinary shared, normal-priority synthetic todos marked with a synthetic-certification reason.
- A reviewed UUID `run_id` deterministically derives every operation UUID. Repeating a plan therefore repeats the same logical operations instead of creating an unbounded second set.
- Operations, rate, concurrency, request timeout, actor count, weights, response size, and thresholds are bounded.
- Cookies and Account UUIDs come only from narrowly named environment variables and are never accepted on the command line or written to evidence.
- Every actor must use a distinct cookie environment reference, Account environment reference, and resolved Account UUID.
- Redirects are refused. Responses must be bounded JSON `201` results with valid Work identity, version, ETag, and Account-scoped Location.
- Evidence contains only reviewed actor labels, release identity, counts, latency, bounded status/error categories, thresholds, and the plan digest. It contains no origin, route, cookie, Account UUID, operation UUID, Work UUID, generated title, request body, response body, Location, ETag, or raw transport error.
- Evidence files use `0600` and exclusive creation; an earlier result cannot be overwritten.

Use only dedicated synthetic Accounts with sufficient reviewed `work.active_items` capacity. Never run this command against an Account containing customer data.

## Plan contract

| Field | Meaning and bound |
|---|---|
| `schema_version` | Exactly `1` |
| `environment` | Reviewed 2-48 character machine label |
| `revision` | Exact 40-character lowercase Git revision |
| `image_digest` | Exact immutable `sha256:` image-index digest |
| `origin` | Exact HTTPS Spyglass application origin without path, credentials, query, or fragment |
| `run_id` | Reviewed UUID unique to this logical certification workload |
| `operations` | `1-500` logical Work creates; each produces exactly two HTTP requests |
| `operations_per_second` | `1-50` aggregate logical-operation pacing ceiling |
| `concurrency` | `1-50` workers |
| `request_timeout_seconds` | `1-60` per HTTP request |
| `max_create_p95_ms` | `1-60000`, evaluated independently for every actor |
| `max_replay_p95_ms` | `1-60000`, evaluated independently for every actor |
| `max_error_rate` | `0-0.25`, evaluated per logical operation and actor |
| `actors` | `1-100` weighted synthetic Accounts |

Actor names are safe evidence labels. Weights are `1-100`, their sum is at most 1,000, and the operation count must cover at least one complete weighted cycle. `cookie_env` must match `SPYGLASS_WRITE_COOKIE_*`; `account_id_env` must match `SPYGLASS_WRITE_ACCOUNT_ID_*`.

## Preparation and execution

1. Bind the plan to the same signed revision and image digest used by the read, failure, and canary profiles.
2. Provision isolated synthetic Accounts with an enabled writable Work package and enough capacity for the distinct deterministic operations.
3. Create least-privilege synthetic member sessions and inject cookies/Account UUIDs from the environment secret manager.
4. Record latency, error, database, connection-pool, admission, routing, HPA, and isolation budgets before execution.
5. Freeze unrelated deployments and synthetic-data changes for the evidence window.

Run from the exact release checkout:

```powershell
wsl.exe -e sh -lc 'go run ./cmd/write-cert -plan ./restricted/write-plan.json -output ./restricted/write-evidence.json'
```

Exit status is `0` for passing evidence, `1` for a valid failing run, and `2` for invalid plan, credential, or evidence output. A failure file remains evidence; use a new filename for a rerun. Reusing the same plan/run UUID safely replays the same operations, but changing thresholds or release identity requires a new reviewed plan and run UUID.

## Evidence interpretation

Each actor result records logical operations, physical requests, errors, error rate, create/replay p50/p95/p99/max latency, bounded create/replay status counts, bounded error categories, and pass/fail. Missing actors, partial scheduling/completion, any create/replay response-identity mismatch, or a threshold breach fails the report.

A passing client report remains incomplete without coincident platform evidence. Archive time-aligned router/API latency and denials, Work admission outcomes, database connections/transactions/locks/IO, HPA state, replica identity, error budgets, and isolation alerts. The resulting Work rows must equal the expected distinct operation count; a replay must not consume another item number, capacity reservation, event, or row. Verify those invariants through the restricted staging assertion job, not by extending this portable report with customer identifiers.

## Cleanup

The generated Work items are durable by design. After all exact-plan reruns and server-side invariant assertions:

1. hash and archive the immutable report and coincident platform exports;
2. revoke synthetic sessions;
3. erase disposable synthetic Accounts through the ordinary audited Account closure/erasure workflow, or retain them under a named synthetic-fixture policy with reviewed capacity;
4. confirm capacity-release and erasure queues settle; and
5. record cleanup evidence in the restricted release manifest.

Do not add an unaudited delete route or direct SQL cleanup merely to make load generation convenient.
